# Feature Spec: Prototype Block Parity for Node Editor

## Objective

Translate the block system shown in `temp/prototype.jsx` into a product spec for the current node experience in `apps/web/app/pages/node/[id].vue` and the workspace schema in `packages/workspace/src/index.ts`.

This spec does four things:

1. Extracts the prototype block inventory in product terms.
2. Describes the current node block system in product terms.
3. Compares prototype parity against the current node implementation.
4. Defines what is missing inside the current node experience and how to close the gap.

## Source Baseline

Prototype source:

- `temp/prototype.jsx`

Current implementation source:

- `apps/web/app/pages/node/[id].vue`
- `packages/workspace/src/index.ts`

## Current Node Editor: What Exists Today

The current node editor is a tabbed document-style workspace. Each node can contain multiple tabs, each tab can contain multiple blocks, and each node can store reusable custom block templates.

### Built-in block types

`Task list`

Purpose: track tasks with completion state and lightweight prioritization.

Data:

- title
- tasks[]
- task text
- completed
- due date
- priority

Behavior:

- add/remove tasks
- inline edit task text
- set due date
- set low/medium/high priority
- progress summary and progress bar

`Notes`

Purpose: freeform written context inside a node.

Data:

- title
- note body

Behavior:

- multiline editing
- autosave
- preview mode with lightweight markdown-like formatting

`Decision`

Purpose: weigh a single decision using pros and cons.

Data:

- title
- pros[]
- cons[]
- each item has text and weight
- final recommendation text

Behavior:

- add/remove pros and cons
- edit weight per item
- derived pros weight
- derived cons weight
- derived decision signal: `lean-yes`, `lean-no`, or `balanced`

`Tracker`

Purpose: log numeric entries and show directional movement.

Data:

- title
- entries[]
- each entry has label, numeric value, createdAt

Behavior:

- add/remove entries
- edit label and value
- derived trend direction
- derived delta
- simple bar visualization

`AI prompt`

Purpose: save a prompt and generate a node-aware output snapshot on demand.

Data:

- title
- prompt
- latest output
- output history

Behavior:

- manual run button
- output history persisted in block
- output is not external-model AI; it is generated by local summarization logic from node data

`Time orchestrator`

Purpose: summarize tasks already stored in task-list blocks.

Data:

- title only

Behavior:

- scans task-list blocks in the current node
- shows overdue tasks
- shows upcoming tasks due within seven days
- shows high priority tasks
- suggests next actions using due date and priority heuristics

`Custom template block`

Purpose: create reusable schema-based form blocks inside a node.

Data:

- template definition stored at node level
- template name
- fields[]
- field types: text, number, checkbox, textarea
- optional notes area
- optional formula
- optional AI prompt template
- block instance values
- optional latest AI output
- output history

Behavior:

- create template inside the node
- reuse the template to create multiple block instances
- simple formula evaluation using numeric fields
- prompt interpolation using field keys
- manual run button for prompt output

### Node-level capabilities

- tabs per node
- local search across block titles and contents
- save block/tab/node to marketplace
- autosave to backend
- hidden custom block template builder

### Current structural limits

- max built-in types are fixed and small
- custom templates only support flat key-value forms
- no nested collections in custom blocks
- no visual block layouts such as kanban, matrix, timeline, or grid
- no real AI provider integration in node blocks

## Prototype Inventory: Domain Modules and Block Details

The prototype is not a single generic block system. It combines two layers:

1. Domain-specific analytical modules.
2. A cross-domain custom block catalog with richer structured layouts.

## Parity Assessment: Prototype vs Current Node

### Strong overlap

`Notes`

Status: present today.

Difference: current node notes are stronger than prototype in editing ergonomics because they include preview and autosave, but they remain plain text rather than structured analysis.

`AI prompt`

Status: partially present today.

Difference: current node stores history and supports manual runs, but it does not call a real model and does not support domain personas or context toggling the way the prototype does.

`Basic numeric tracking`

Status: partially present today.

Difference: current tracker handles entries and trend, but lacks explicit goal tracking, unit semantics, richer card-style summaries, and prototype-style chart interaction.

`Simple weighted comparison`

Status: partially present today.

Difference: the current decision block supports weighted pros and cons for one choice, but it does not support multi-option weighted criteria like the prototype decision matrix.

### Partial overlap via current custom templates

`Form-style custom tools`

Status: present today.

Difference: current custom templates are useful for flat structured data entry. They cannot represent the prototype's nested, repeatable, or visual block types without major extensions.

## What Is Missing Specifically at Node Level

This is the core gap list for `@node`.

### 1. The node data model is too flat for prototype parity

Current node blocks only support:

- flat arrays of tasks
- flat note bodies
- flat pros/cons arrays
- flat tracker entries
- flat custom key-value maps

Prototype parity requires nested and typed collections such as:

- objectives with nested key results
- criteria with nested per-option scoring
- team x skill matrices
- kanban columns with card arrays
- milestone arrays with status workflows
- quadrant items with coordinates
- habit grids
- table schemas with dynamic columns and rows

### 2. The current custom block system cannot represent structured mini-apps

Current custom templates can model:

- text fields
- number fields
- checkboxes
- textareas
- a single calculated value
- a prompt template

They cannot model:

- repeatable nested lists
- row/column datasets
- multi-column boards
- charts
- grids
- timelines
- quadrant layouts
- matrix visualizations
- per-item status workflows

### 3. The current time orchestrator is a summary block, not an operating block

Current node orchestrator:

- only reads task-list blocks
- only understands priority and due date
- cannot edit a richer task model
- cannot reason about domain allocation
- cannot display urgency vs importance

Prototype orchestrator requires:

- a dedicated task schema inside the orchestrator or a richer shared task schema
- domain field
- urgency
- importance
- estimated minutes
- direct task editing
- time rollups by domain
- Eisenhower classification

### 4. The node editor lacks most prototype analytical blocks as first-class tools

Prototype modules are not generic forms. Many are opinionated decision-support tools with fixed layouts and derived metrics. The current node page has no native equivalents.

### 5. The current AI behavior is placeholder logic, not real agent behavior

Current node AI blocks:

- generate deterministic summaries from local node state
- do not call a provider
- do not have domain-specific system roles
- do not support chat

Prototype AI behavior includes:

- domain-specific agents
- manual prompt execution against a real model
- context packaging
- orchestration-style prioritization prompts

### 6. The current node UX is linear-card based only

Prototype parity needs richer visual surfaces:

- quadrant canvases
- matrices
- timeline tracks
- scorecards
- heat maps
- kanban columns
- funnel stages
- radar charts

Current node blocks all render as vertically stacked form cards.

## Recommended Product Direction

### Recommendation

Do not attempt to force all prototype parity through the existing custom template block.

Instead, use a two-track approach:

`Track A: add first-class typed analytical blocks for high-value prototype modules`

Use this for blocks whose value comes from fixed semantics and visualization:

- OKR Tracker
- Decision Matrix
- Business Model Canvas
- Skills Heat Map
- Delegation Recovery
- 9-Box Grid
- Deal Scoring
- Sales Funnel
- Content Pipeline
- Content Radar
- Authority Scorecard
- Hook Bank
- Profitability
- Pricing Simulator
- Course Roadmap
- Orchestrator V2

`Track B: evolve custom blocks from flat forms into structured layout blocks`

Use this for reusable generic mini-app patterns:

- Table
- Checklist
- Kanban
- Scorecard
- SWOT
- Tracker V2
- Pros & Cons
- Habit Grid
- Process
- 2x2 Matrix
- Timeline
- AI Prompt

This keeps the current flat custom template system intact for simple forms while introducing a richer second layer for structured blocks.

## Proposed Scope by Phase

### Phase 1: Highest-value parity inside node

Goal: close the biggest product gap quickly with the smallest number of new typed blocks.

Include:

- OKR Tracker block
- Decision Matrix block
- Business Model Canvas block
- Content Pipeline block
- Deal Scoring block
- Orchestrator V2 block
- real AI provider execution for AI prompt blocks

Reason:

- these blocks are closest to the product's value proposition
- they are hard to fake with current custom templates
- they materially improve node usefulness for planning and execution

### Phase 2: Structured custom block engine

Goal: make the node editor capable of hosting prototype-style mini-tools without adding dozens of bespoke block types.

Include:

- table
- checklist
- kanban
- scorecard
- SWOT
- timeline
- process
- 2x2 matrix
- habit grid

Reason:

- these are reusable layouts across domains
- they unblock broad parity with the prototype custom block catalog

### Phase 3: Domain intelligence layer

Goal: bring the domain-specific feeling of the prototype into the node experience.

Include:

- domain presets for starter nodes
- domain-aware AI roles
- quick-insert packs per domain
- saved node templates that compose multiple blocks

## Acceptance Criteria for Prototype Parity at Node Level

Prototype parity should be considered reached when:

- a user can open a node and create the main analytical tools from the prototype as native blocks
- a user can create structured generic blocks beyond flat form templates
- the orchestrator inside a node can directly edit and prioritize rich tasks
- AI prompt blocks can run against a real provider on click
- node blocks can express matrix, board, grid, timeline, and scorecard layouts
- the custom block system can support nested and repeatable content instead of only flat fields

## Summary

The current node editor already has a solid foundation:

- tabs
- autosave
- search
- marketplace export
- simple built-in blocks
- flat custom block templates

But it is still much narrower than the prototype.

The prototype is effectively a library of domain-native operating tools plus a richer catalog of structured mini-app blocks. The main missing piece at `@node` is not styling. It is expressive block semantics.

The core product decision is:

- keep flat custom templates for simple forms
- add first-class analytical blocks for high-value domain tools
- add a second structured custom block layer for reusable visual mini-apps

That approach matches the current architecture better than trying to stretch the existing `custom` block into every prototype shape.
